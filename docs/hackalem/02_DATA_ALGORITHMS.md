## 2. Проверки, без которых расчёт не начинается

1. Проверить наличие трёх файлов и обязательных колонок; лишние колонки разрешить с записью в отчёт, не использовать автоматически.
2. gid/src/dst читать без float-преобразования. Уникальность gid, целочисленность depth и n_tx, логический is_seed, существование всех концов рёбер.
3. Проверить отсутствие null, бесконечностей, отрицательных/нулевых сумм и n_tx<1. Не подставлять молча ноль вместо повреждённого значения.
4. Проверить уникальность пары src,dst в edges. Полностью повторяющиеся строки transactions **сохранять**: в исходнике 97 повторов после первого вхождения, отдельного transaction_id нет. Совпадающие платежи могут быть разными операциями.
5. Преобразовать сумму в тиыны округлением к ближайшему целому после проверки `abs(100*x - round(100*x)) <= 1e-6`. В текущем наборе максимальное отклонение ≈1,86e-9 тиына; проблема только представления float. Если точность хуже — остановиться и показать строку, не менять деньги молча.
6. Сгруппировать transactions по src,dst. Сверить **пары, количество и суммы** с edges. Допуск сравнения исходных агрегатов — не более 1 тиына; расхождение не скрывать. Для последующих расчётов использовать канонические суммы из transactions в целых тиынах, сохранив оригинальные файлы.
7. Проверить диапазон дат, порог, depth и соответствие seed/depth=0. Не исправлять исходник автоматически.
8. Добавить в граф все nodes, затем рёбра. Проверить 2 248 вершин, включая 19 изолятов.
9. В данном наборе нет self-loop. Если он обнаружится при повторной загрузке изменённых данных, выпускать явную ошибку неподдержанного входа до расширения правил; не считать собственный перевод признаком организации.
10. Записать SHA-256 каждого файла, размер, строки, результат сверки и версию алгоритма в manifest.

Числа этого датасета — регрессионный контроль официального входа, не хардкод результатов. Алгоритмы должны работать на небольших искусственных тестовых графах другой формы. Функция загрузки не должна требовать ровно 2 248 строк для любого теста; профиль `official` отдельно проверяет ожидаемый набор и его hash.

## 3. Критическая точность идентификаторов

gid лежат в диапазоне **100000000011452100…100000008782800100**, выше 2^53−1. Поэтому:

- Python/pandas/CSV: int64 или Python int, точная десятичная запись.
- JSON, URL, TypeScript, Cytoscape IDs, `localStorage`: строка цифр.
- Запрещены `Number(gid)`, `parseInt(gid)`, `float(gid)`, преобразование DataFrame с gid в float-массив.
- Не использовать `iterrows()` для переноса смешанных числовых строк с gid; брать типизированные колонки или `itertuples()`.
- `top_gids` — строка с gid через `;`; JSON — массив строк.
- При импорте CSV в Excel колонку gid нужно импортировать как текст. Это не повод менять обязательную CSV-схему или добавлять формулы Excel.

Ограничение безопасного целого JavaScript описано в [MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER). Для UI строка проще и надёжнее BigInt, который нельзя непосредственно сериализовать обычным JSON.

## 4. Граф и базовые признаки

`G` — ориентированный граф; узлы отсортированы по gid, рёбра по (src,dst) перед добавлением. Денежный вес хранится в тиынах; метрики, которым нужен float, получают отдельное числовое представление без изменения gid.

Для каждого узла v:

| Поле | Определение |
|---|---|
| in_degree / out_degree | Число различных наблюдаемых отправителей / получателей |
| in_tiyin / out_tiyin | Сумма входящих / исходящих наблюдаемых переводов |
| in_tx / out_tx | Число соответствующих транзакций, включая одинаковые строки |
| observed_ratio | out/in при in>0, иначе null; не полный баланс |
| boundary | depth=4 и out_degree=0 |
| isolated | in_degree=0 и out_degree=0 |
| seed_reach_count | Число разных seed, от которых есть ориентированный путь к v длиной 1…4; сам seed в своём счётчике исключён |
| pagerank | Взвешенный PageRank, alpha=0.85, weight=sum_tiyin, tol=1e-8, max_iter=500 |
| betweenness | Приближённая ориентированная посредническая центральность, k=min(128,N), normalized=True, weight=None, seed=42 |
| participation | Разнообразие соседних кластеров по обороту: 1−Σ(w_c/Σw_c)^2; 0 при отсутствии связей |

PageRank при отсутствии рёбер не использовать как сигнал приоритета изолята. Невозможность сходимости после заданного лимита — явная ошибка вычисления, а не невидимая подмена метрики. Выходные роли не должны зависеть от внешнего LLM.

Посредническая центральность использует невзвешенные кратчайшие пути: сумма перевода не является расстоянием. Приближение и фиксированная выборка описываются в справке. [NetworkX](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.centrality.betweenness_centrality.html) трактует weight как расстояние; передавать туда sum_kzt без обоснованного преобразования нельзя.

Seed-достижимость — BFS из каждого seed, максимум четыре шага, с visited для защиты от циклов. Она показывает связь в наблюдаемой топологии, а не доказанное происхождение денег. `participation` суммирует входящие и исходящие обороты по кластеру контрагента; встречные направления учитываются оба.

## 5. Кластеризация

Порядок зависимостей: базовые признаки и центральности → cluster membership → participation → роли → priority → итоговая статистика кластеров и top_gids. Разбиение не зависит от ролей/priority; это устраняет циклическую зависимость между составом кластера и его топом.

1. Сохранить ориентированный G для потоков и ролей.
2. Построить неориентированную проекцию U: для пары {u,v} вес равен сумме переводов обоих направлений. Нельзя терять один из весов обычным `to_undirected()` при встречных рёбрах.
3. Для вершин с рёбрами применить Louvain: weight=sum_tiyin, resolution=1.0, threshold=1e-7, seed=42. Вставка отсортирована, зависимости зафиксированы.
4. Если в выданном сообществе несколько связных компонент, разделить их. Изоляты — отдельные singleton-кластеры.
5. Стабильные ID: отсортировать группы по убыванию размера, затем по минимальному gid, присвоить 1…K.
6. `sum_kzt_internal` — сумма ориентированных исходных рёбер, оба конца которых в кластере; каждое исходное ребро ровно один раз. Межкластерные рёбра отдельно, не прибавлять их к двум внутренним оборотам.
7. `top_gids`: до трёх узлов кластера по финальному priority_score, равенство разрешается меньшим gid. Гипотеза формируется по составу ролей и наблюдаемой структуре, помечается как гипотеза.

Louvain — эвристика, параметр resolution влияет на детализацию; документация [NetworkX Louvain](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.community.louvain.louvain_communities.html). Кластер не равен преступной группе. Число «8 сообществ с несколькими seed» из примечания постановщика не является обязательным ответом; запрещено подгонять к нему разбиение.

## 6. Нормализация и семантика score

Обозначение `P(x)` — эмпирический ранг положительного признака среди положительных значений этого же признака на всём наборе: `count(0 < values <= x) / count(values > 0)`. Если x≤0 или положительных значений нет, P=0. Одинаковые значения имеют одинаковый ранг. Это относительное положение, не вероятность. Для степеней применяется та же функция; их нулевые значения не получают высокий ранг.

`clip(x)=max(0,min(1,x))`. В формулах I=in_tiyin, O=out_tiyin, a=in_degree, b=out_degree, s=seed_reach_count, r=observed_ratio, B=betweenness, PR=pagerank, C=participation.

**Предлагаемые пороги — первоначальная версия правил, ещё не валидированная модель.** Они согласованы с фактическим распределением степеней, но должны пройти ручной разбор и чувствительность на этапе A2. Любая корректировка — единое правило для всех узлов, config diff, объяснение и повтор проверок; нельзя менять роль отдельного gid.

## 7. Шесть ролей: точные правила v1

Сначала получить кандидатов и raw_score. Не заставлять набор содержать все шесть ролей, если критерии не выполняются. Для изолята немедленно `peripheral`, score=0.

| Роль | Условие допустимости | Raw score |
|---|---|---|
| consolidator | a≥3 | 0.45·clip(a/8)+0.25·P(I)+0.30·clip(s/3) |
| distributor | b≥5 | 0.60·clip(b/20)+0.40·P(O) |
| transit | не seed, не boundary, a≥1, b≥1, I>0, 0.8≤r≤1.2 | 0.60·clip(1−abs(1−r)/0.2)+0.20·clip(min(a,b)/3)+0.20·P(min(I,O)) |
| terminal | не seed, depth<4, a≥1, b=0, I>0 | 0.50+0.25·P(I)+0.25·clip(a/3) |
| coordinator | depth<4, a≥2, b≥2, s≥2, C≥0.30, P(B)≥0.90 | 0.35·P(B)+0.25·C+0.20·clip(s/5)+0.20·P(PR) |
| peripheral | нет допустимого кандидата либо изолят | 0.20 при наблюдаемых связях, 0 при изоляции |

Нормализация `P(min(I,O))` строится по вектору min(I,O) всех узлов. Если допускается несколько ролей, победитель — максимальный raw_score. Равенство разрешается фиксированным порядком: coordinator, consolidator, distributor, transit, terminal. Эти правила выбирают **основной наблюдаемый структурный профиль**, не исключая совмещение нескольких функций.

После выбора основной роли вычислить `role_score = min(raw_score, все применимые caps)`:

- coordinator: cap=0.55; структура не устанавливает управление или организаторскую роль;
- terminal: cap=0.65; даже до четвёртого колена нет полной банковской картины;
- boundary: cap=0.65;
- seed: cap=0.65; само наличие в исходном списке не определяет функцию;
- in_tx+out_tx≤1: cap=0.45;
- остальные случаи cap=1.

Cap — консервативное соглашение команды, а не статистическая калибровка. Хранить raw_score, caps и final score в объяснении. Для альтернативной роли показать её собственный raw_score/capped_score и условия, но основной выбор определяется raw_score по опубликованному правилу. Не называть эти значения вероятностью; не перемножать их как независимые события.

`terminal` в CSV сохраняет обязательное имя словаря. Видимая подпись UI: **«Наблюдаемый конец маршрута»**. `coordinator`: **«Структурный кандидат на координацию»**. Отсутствие кандидата означает недостаток признаков, а не «узел безопасен».

Boundary может получить consolidator при наблюдаемом fan-in; запрещён именно вывод terminal на основании обрезанного выхода. У seed r можно показать как сырое отношение с пояснением, но оно не допускает transit/terminal и не используется как баланс. Для любого узла O>I не доказывает аномалию: входящие извне выборки неизвестны.

## 8. Приоритет проверки

Для связанного узла:

`priority = 0.30·P(I+O) + 0.25·P(B) + 0.20·clip(s/5) + 0.15·max(P(a),P(b)) + 0.10·C`

Для изолята priority=0. Сортировка: по убыванию **неокруглённого** priority, затем по gid по возрастанию. В CSV score записать с 6 знаками, в UI показывать 0–100 с одним знаком, сохраняя полный score в snapshot. Top = первые min(50,N); при официальном N он содержит 50 строк и удовлетворяет ≥20.

Каждое из пяти слагаемых отдаётся отдельно в API: raw value, normalized value, weight, contribution. Их сумма должна совпадать с priority с допуском 1e-12. `why` строится из двух наибольших вкладов плюс существенный флаг ограничения. Округление отображения не должно менять ранжирование.

Не использовать `is_seed` как непосредственный бонус и не приравнивать PageRank к виновности. Не умножать приоритет на role_score: это спрятало бы важные узлы с недостаточной наблюдаемостью. Не писать «80% вероятность преступления» для score=0.8.

## 9. Evidence и альтернативные гипотезы

`evidence` в CSV ≤200 Unicode-символов, непустой, содержит проверяемые числа. Формирование детерминированное по роли; ограничение длины проверять до экспорта. Сокращать заранее заданные фразы, не обрывать смысл посередине числа.

Структура полного объяснения:

1. role_rule_id и версия config;
2. условие, порог, фактическое значение и pass/fail;
3. raw_score и ограничения score;
4. два основных вклада в priority;
5. supporting_transfers: ссылки на связанные исходные строки, общий count и возможность открыть весь список;
6. альтернатива из остальных допустимых ролей; если их нет — «данных недостаточно для другой роли» с непрошедшими условиями, без искусственной второй классификации;
7. флаги и следующий запрос данных.

Альтернативы — не вероятности, не взаимоисключающие уголовные версии. Для consolidator vs distributor можно показать, что узел и собирает, и распределяет. Для boundary «транзит за пределами выгрузки» — не присвоенная роль, а непроверяемая пока возможность.

## 11. Расширения с ограниченным объёмом

### E1. Структурная симуляция — первая очередь

Выбрать 1–3 узла и удалить их из копии графа. Базовая линия — связность тех же оставшихся вершин в исходном графе, где удаляемые вершины ещё могут соединять пути. Пусть R — оставшиеся вершины. `before_pairs = Σ choose(|C ∩ R|,2)` по слабым компонентам исходного графа; `after_pairs = Σ choose(|C'|,2)` по компонентам графа после удаления. Показывать потерю связных пар `(before_pairs−after_pairs)/before_pairs`, если before_pairs>0, иначе null с подписью «не определено».

Также показать число оставшихся компонент, размер крупнейшей относительно |R| и число удалённых рёбер. Считать при нажатии, кэш по run_id и отсортированным gid. Удалённые узлы не входят в знаменатель, иначе получится искусственный эффект. Исходные CSV и роли не менять. Это топологическая чувствительность: нельзя переводить её в предотвращённые потери, замороженные средства или прогноз поведения людей.

### E2. Время — только если есть запас после E1

Точность date — день, не timestamp. Для узла агрегировать входящие/исходящие по дням. Событие согласованности: положительный вход в день d и положительный выход в d+1 или d+2. Число таких входных дней делится на число дней с входом, у которых в наблюдаемом периоде присутствует полный горизонт d+2; последние два дня исключаются из знаменателя. Если знаменатель 0 — null. События одного дня показывать отдельно без утверждения о порядке. Это согласованность активностей, не доказанное прохождение тех же денег.

Не включать этот показатель в основные роли задним числом без новой версии правил и повторной приёмки. Дополнительная карточка и дневные столбики достаточны. Полный поиск `all_simple_paths` и перечисление всех циклов запрещены в горячем пути: ограничения времени важнее.

## 12. Устойчивость и честные границы

- Перемешивание строк не меняет роли/скоры/кластеры после канонической сортировки; source_row продолжает ссылаться на исходную физическую строку файла.
- Два запуска на одинаковых файлах/config/зависимостях дают одинаковые CSV. Время запуска хранится отдельно от детерминированного run_id.
- Проверить чувствительность: пороги a=3 и b=5 изменяются ±1, границы r — ±0.05, Louvain resolution 0.8/1.0/1.2. Сравнить долю изменённых ролей и пересечение top-20. Это диагностика, не перебор ради красивого ответа. При нехватке времени не заявлять, что проверка проведена.
- Не заявлять accuracy, recall или F1 на официальном наборе: нет ground truth. Мини-графы проверяют корректность правил, а не доказанную реальную классификацию.
- Для миллиона узлов потребуются колоночная обработка, более эффективный графовый движок, ограниченные/приближённые центральности, предрасчёт соседств и уровни детализации UI. В MVP это описывается, не реализуется.
