## 3. Что начать сразу, не ожидая backend

На согласованном fixture создавай layout, состояния, типы, длинные ID, граф и карточку. На fixture должен быть явный marker «Тестовый контракт». После получения API заменить fixture; production не должен молча падать обратно в фальшивые данные.

Если Мейрам ещё не выдал fixture, используй формы из 03_ARCHITECTURE_CONTRACTS.md, согласуй имена полей одним сообщением и работай над статической компоновкой/стилями. Не придумывай новые поля `risk`, `criminal_probability`, `customer_name`.

## 6. Ключевые сценарии твоей приёмки

1. Открыть очередь и выбрать узел: один и тот же gid в строке, графе и карточке.
2. Ввести полный 18-значный gid. Он хранится строкой, копируется точно, не округляется.
3. Видеть направление исходного ребра и суммы. Все ID Cytoscape совпадают с source/target контракта.
4. Увидеть два разных понятия: «Соответствие правилу» и «Приоритет проверки», не вероятность вины.
5. Открыть supporting facts, условия/пороги и альтернативу; никакого придуманного текста.
6. Кликнуть входящую сумму и проверить таблицу исходных переводов. Сумма total не равна случайно сумме одной страницы.
7. Найти boundary: видимое предупреждение, не «деньги осели». Найти изолированный seed: один узел, ноль рёбер, непустая карточка.
8. Быстро переключить A→B: поздний response A не перезаписывает B.
9. Поиск через активный фильтр всё равно находит gid в полном наборе.
10. Empty/error/unknown gid имеют конкретный текст и действие, без бесконечного spinner.
11. Скачать настоящий CSV текущего run_id. Никаких кнопок-заглушек.
12. 1440×900, 1280×800, 1024×768, keyboard focus/Enter/Escape; нет наложений или потери действий.

Ограниченный ego-граф показывает «X из Y», не скрывает лимит. Цвет роли дублируется подписью. Из canvas должен быть доступен путь к обычной таблице данных. При закрытии компонента Cytoscape очищается.

## 7. Передача Мейраму

После этапа: свой commit SHA, что реально работает, какие API вызовы используются, какие тесты/браузерные сценарии прошли, что осталось. Push в официальный remote регулярно, минимум до границы каждого отчётного часа. Не редактировать main напрямую одновременно с интеграцией Мейрама.

Перед релизом:

```bash
npm ci
npm test -- --run
npm run build
```

Команды из web; их scripts надо реализовать и проверить. Для E2E использовать согласованный `npm run test:e2e`; если автоматизация недоступна, выполнить все сценарии вручную и записать это честно. Не говорить «тесты пройдены», если проверен только build.

## 8. Демонстрация и чистый запуск

Ты — независимый проверяющий README Мейрама: новый clone, новое окружение, ровно перечисленные команды, никаких личных .env/подписок. После установки отключить сеть и пройти UI. Записать реальные OS/hardware/время/проблемы в validation. Неправильная инструкция исправляется и повторяется.

Демо: проблема → живой pipeline → приоритетный узел → evidence/переводы → альтернатива → boundary → произвольный gid → выгрузки/ограничения. Подробный тайминг в 07_RULES_DELIVERY.md. Конкретные примеры выбираются по готовому расчёту; не зашиваются в приложение. Сценарий должен длиться ≤5 минут.
