Источник: [официальное положение на платформе](https://edu.astanahub.com/hackathons/df4743f5-c492-415c-b45a-1f13adb78e06), снимок `sources/rules-extracted.txt`; требования кейса — [официальное ТЗ Finance](https://docs.google.com/document/d/1JPLU-G6R25Ge2hVaY2J9cqvrx7FGExj87XKwJPaMz3o/edit). Ни эта выжимка, ни AI не могут подтвердить допуск вместо организатора. Ниже только применимые требования и конкретный способ их соблюдать.

Строгость соблюдения означает факты и историю, а не добавление вымышленных запретов. Положение прямо разрешает вспомогательные заготовки и AI; оно запрещает представлять заранее готовое ядро как разработанное за время хакатона. Подробное проектирование в текущем окне фиксируется честно. Решение вопроса о допустимости спорного стороннего компонента остаётся за организатором.

## 2. Почасовая фиксация

Час 1: 13:00–14:00; час 2: 14:00–15:00; час 3: 15:00–16:00; час 4: 16:00–17:00; час 5: 17:00–18:00. Документировать реальную работу внутри каждого интервала. Не создавать пять пустых отчётов заранее как «подтверждение».

Достаточные по типу примеры из положения: реальные изменения в репозитории, функционал, прототип, дизайн, архитектура, тестирование, подготовленные данные. Окончательную достаточность подтверждает организатор. Для нашей работы: источник+аудит/контракты → расчёт+API → работающий UI → проверенный релизный кандидат → финальная сборка+подача. Если фактический график отличается, записывать фактический результат, не копировать ожидаемый.

Общие коммиты не обязаны быть привязаны ровно к границе часа. Делать содержательные коммиты после небольших законченных задач и push регулярно; перед :50 проверить, что есть подтверждение текущего часа. Не менять даты, не переписывать историю, не добавлять пустые коммиты ради видимости.

## 3. Правила данных и выводов кейса

Данные только для хакатона, gid синтетический. Не обогащать внешними источниками, не угадывать ФИО/ИИН/возраст/пол/организацию. Не загружать банковские данные в необязательные сторонние сервисы без необходимости; MVP работает локально. Не обучать модель с неизвестной размёткой и не заявлять accuracy, которой никто не измерял.

Нельзя хардкодить «правильные» gid, выдавать роль без объяснимого критерия, требовать GPU/облачный кластер/платный сервис для воспроизведения. Граничный обрыв, неполные входящие, порог, период и отсутствие атрибутов обязательно отражать в выводах. Термины интерфейса — «гипотеза», «признаки», «приоритет проверки», не «доказанный преступник».

Не менять приватность репозитория ради удобства демо. Доступ организатора и второго участника проверять отдельно. Датасет не публиковать как общий open-data ресурс и не переносить под лицензию собственного кода.

## 4. Контрольный список подачи

- [ ] В платформе выбран Finance / «Граф денег».
- [ ] В официальном remote есть полная актуальная история двух участников и результаты каждого часа.
- [ ] README описывает фактическое приложение и проверенную команду, а не только этот план.
- [ ] Команда `python run.py` реализована, raw pipeline создаёт все три CSV <300 секунд.
- [ ] Все 2 248 узлов присутствуют, top≥20, кластеры заполнены, роли объясняются по критериям.
- [ ] UI показывает направления, роли/кластеры, находит любой gid, изолят и boundary обработаны.
- [ ] В репозитории есть результаты, manifest, исходники UI и его локальная сборка.
- [ ] Внешние компоненты и исходный starter раскрыты, ключей/паролей/личного .env нет.
- [ ] Один участник воспроизвёл запуск другого из нового clone.
- [ ] Приложение после установки работает без сети и без подписки участника.
- [ ] Архитектурная диаграмма и 5-минутный демо-сценарий соответствуют реально готовой версии.
- [ ] Итоговый commit SHA записан и виден на remote до 18:00.
- [ ] Решение действительно отправлено через предусмотренный канал платформы, подтверждение сохранено.

Ни наличие плана, ни загрузка dataset/starter не закрывают эти пункты. Капитан отвечает за фактическую подачу; AI отмечает её только по наблюдаемому подтверждению.

## 5. README итогового приложения

Верх README перед релизом должен содержать: что делает рабочее решение; что установлено/поддерживается; точную установку и одну команду запуска; где UI и три CSV; способ проверить сценарий. Далее: архитектура; формулы и пороги с версией; ограничения; offline; сведения о тестовой машине/времени; сторонние материалы; масштабирование до миллиона; известные ограничения.

До реализации README честно сообщает «планирование». Нельзя вставить непротестированную будущую команду под заголовком «готовый запуск» и объявить проект воспроизводимым.

## 6. Сценарий демо на пять минут

| Время | Действие | Тезис |
|---|---|---|
| 0:00–0:30 | Показать задачу и готовое рабочее место | 81 исходный seed, 2 248 узлов; нужно выбрать следующий объект проверки |
| 0:30–1:05 | Живой запуск pipeline, показать время/CSV | Результат пересчитывается из raw, а не зашит в интерфейс |
| 1:05–2:00 | Открыть рассчитанный приоритетный узел | Роль, числа, вклад в priority, исходные переводы |
| 2:00–2:45 | Показать альтернативу и ограничения | Гипотезу можно проверить и опровергнуть |
| 2:45–3:25 | Открыть boundary-узел | Мы учитываем обрыв выгрузки и не называем его доказанным стоком |
| 3:25–4:15 | Поиск gid, выбранного жюри; при запасе изолят | Нет преднастроенного списка «правильных» узлов |
| 4:15–4:40 | E1, если реализован; иначе кластер и экспорт | Структурное объяснение и готовые артефакты |
| 4:40–5:00 | Ограничения и развитие | Локальная проверка сейчас, расширение данных и масштаба следующим шагом |

При выборе конкретных 2–3 узлов для репетиции использовать результаты реального pipeline: сильный профиль, boundary и при необходимости mixed-role. Их можно записать в docs/demo.md как примеры демонстрации, но нельзя зашивать в алгоритм роли. Если живой pipeline требует больше выделенных 35 секунд, сократить речи и запустить его в начале; полный лимит ТЗ остаётся <5 минут, целевой <60 секунд.

Вопросы жюри: «Почему этот score?» → пять вкладов и ограничения; «Почему coordinator?» → структурный кандидат, критерии и cap; «Это точная трассировка денег?» → нет, наблюдаемые переводы/топология; «Где accuracy?» → нет размеченных ролей, проверена обоснованность правил; «Почему не LLM?» → факты и роли воспроизводимы, AI использован в разработке, необязательный ассистент можно надстроить без подмены расчёта.
