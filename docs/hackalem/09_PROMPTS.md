# Промпты для двух участников и проверки

Промпты применяются после того, как человек поручает реализацию. Каждый инструмент должен иметь checkout **официального репозитория**, а не папку с одним экспортированным документом. Не запускать одновременно два пишущих AI в одном checkout. Имена моделей не являются обязательными: используйте фактически доступные в ваших Codex/Claude Code настройки.

## 1. Мейрам (A) — ядро и интеграция

```text
Ты реализуешь backend и аналитическое ядро Neverlose для Finance-кейса HackAlem AI 2026.
Работай в официальном repo BAITC-Hacks/hack-1eeed6ff-s-ztech, ветка codex/analysis-core.

Сначала прочитай AGENTS.md, README.md, docs/hackalem/STATUS.md,
08_SESSION_CONTEXT.md, 01_PRODUCT_SPEC.md, 02_DATA_ALGORITHMS.md,
03_ARCHITECTURE_CONTRACTS.md, 05_IMPLEMENTATION_PLAN.md,
06_QUALITY_GATES.md, 07_RULES_DELIVERY.md и 11_README_REQUIREMENTS.md.

Главный приоритет пользователя — строгое соблюдение официального положения.
Проверь актуальное время: 23.09.2026 окно 13:00–18:00 Астана, не новый отсчёт с этой сессии.
Проверь git status/log, фактическую реализацию и уже пройденные этапы. Не повторяй готовую работу.
До 18:00 сохранить настоящую историю, почасовые результаты, итоговую проверку и подачу.

Твоя зона: app/, config/, tests/ Python, run.py, Python locks, results/,
root README, THIRD_PARTY, общие контракты и интеграция main.
Не изменяй web/ одновременно с участником B. Контракт v1 менять только с передачей B.

Старт: самый ранний незавершённый A-этап из плана. Сначала работающий pipeline,
потом роли/кластеры/priority, затем API и объяснения. Выдай B контракт/fixture сразу,
реальный snapshot и API как можно раньше. Fixture явно тестовый, не финальный результат.

Критично: gid int64 не превращается во float, в JSON gid строка;
деньги в тиынах; 97 совпадающих tx не удалять; все изоляты сохранить;
depth=4/out=0 не означает terminal; seed ratio не полный баланс.
Скоры эвристические, выводы гипотетические; без внешнего обогащения и hardcoded gid.
Основной сценарий без API-ключей, GPU, платного сервиса или личной подписки.

После каждого этапа: смысловые тесты → отдельный review diff → исправить P0/P1 →
повторить затронутые проверки → обновить журнал/STATUS → commit/push.
Отчёт содержит конкретные команды, exit codes и ограничения, а не общую похвалу.
Дополнительные функции только после G3 и при достаточном остатке времени.
Максимум 5–10 минут review этапа; не уходить в бесконечный рефакторинг.

README — часть результата с весом 25 баллов в технической рубрике.
Заполняй его только фактическими инструкциями, измерениями и поддержанными режимами.
Не заявляй готовность приложения, чистый запуск или подачу без проверки.
Продолжай автономно в своей зоне до завершения согласованного этапа;
спрашивай только действительно блокирующие сведения, не повторяй уже принятые решения.
```

## 2. Алишер (B) — аналитический интерфейс

```text
Ты реализуешь интерфейс Neverlose для Finance-кейса HackAlem AI 2026.
Работай в официальном repo BAITC-Hacks/hack-1eeed6ff-s-ztech, ветка codex/workspace-ui.
Прочитай AGENTS.md, README.md, docs/hackalem/STATUS.md, 08_SESSION_CONTEXT.md,
01_PRODUCT_SPEC.md, 03_ARCHITECTURE_CONTRACTS.md, 04_INTERFACE.md,
05_IMPLEMENTATION_PLAN.md, 06_QUALITY_GATES.md и 07_RULES_DELIVERY.md.

Проверь реальное время до 18:00 Астана и текущий код. План не даёт новые пять часов.
Главный приоритет — положение хакатона, воспроизводимость и обязательный сценарий.

Твоя зона: web/, frontend dependencies/lock, UI/unit/e2e tests,
docs/demo.md и docs/architecture.md. Backend, формулы, API и root README ведёт A.
Не меняй контракт самовольно и не пересчитывай роли/priority в браузере.

Создай строго профессиональное рабочее место аналитика, без AI-slop,
без шаблонных AI-экранов, БЕЗ ГРАДИЕНТОВ, без glow/glass/mesh/aurora/hero.
Плоские нейтральные поверхности, тонкие границы, сильная типографика,
цвет только для семантики. На первом экране очередь, направленный граф и карточка.
Никаких декоративных искр, псевдопроцентов, фальшивого «AI думает».

Начни с B1 на согласованном synthetic fixture; явно маркируй fixture.
Когда A отдаст API, подключи реальные данные и убери production synthetic fallback.
Ключевой flow: priority → gid → graph → role evidence → alternative → transfers.
gid всегда string; полный 18-значный ID должен копироваться/искаться без потерь.
Узлы boundary и isolated доступны и понятны; не обвиняй владельцев счетов.
У каждого числа есть единицы и основание. Таблица переводов хранит повторяющиеся строки.
Покажи ограничения графа X из Y и не выдавай скрытые связи за отсутствующие.

После каждого этапа: unit/build → браузерная проверка реальных состояний → review →
исправления P0/P1 → журнал B → commit/push → передача A точного SHA.
Проверь 1440×900, 1280×800 и 1024×768, keyboard/focus, stale response,
empty/error/not found/boundary/isolate, скачивание CSV.
Build без браузера не считается визуальной проверкой.

Перед релизом ты проверяешь новый clone на своём ноутбуке строго по README A,
без скрытых .env/подписок/файлов. Готовишь и репетируешь 5-минутное демо.
Продолжай автономно по своим этапам; scope сокращай по плану, не ломая must-have.
```

## 3. Проверяющий после этапа

```text
Выполни read-only review текущего этапа Neverlose. Не переписывай код самостоятельно.
Прочитай цель этапа, официальные ограничения из docs/hackalem/07_RULES_DELIVERY.md,
контракт и матрицу docs/hackalem/06_QUALITY_GATES.md. Проверь текущий diff и результаты команд.

Ищи конкретные дефекты: нарушение правил/сроков, потеря gid или денег,
потерянные узлы/повторы tx, неправильные boundary/seed выводы,
ошибочная математика, несоответствие UI/API/CSV, stale UI, ложные заявления о готовности,
неработающий чистый запуск, платная зависимость, запрещённый визуал.

Для каждого дефекта: P0/P1/P2/P3, файл/сценарий, как воспроизвести,
ожидаемое и фактическое, минимальная правка, какой тест подтвердит исправление.
Не создавай фиктивные проблемы и не предлагай архитектурный передел без основания.
Если фактического результата команды нет, пиши «не проверено».

Итог: PASS / FAIL / BLOCKED и перечень доказательств. PASS только в границах этапа.
Не путай прохождение тестов с доказанным качеством AML-классификации: ground truth нет.
Временной бюджет review — 5–10 минут, приоритет P0/P1. Отдельно отметь границы проверки.
```

## 4. Возобновление после новой сессии

```text
Продолжи Neverlose в моей зоне A либо B, указанной в текущем сообщении.
Сначала AGENTS.md → docs/hackalem/08_SESSION_CONTEXT.md → STATUS.md → git status/log →
свой журнал docs/progress/ → спецификация и контракт соответствующего этапа.
Определи, что уже реализовано и действительно проверено. Не начинай заново.
Прочитай время до официальных 18:00 Астана; выбери оставшийся scope по плану.
Кратко зафиксируй: этап, следующий результат, блокеры, время до дедлайна.
Затем продолжи самый ранний незавершённый этап с обязательной проверкой и журналом.
Если deadline уже прошёл, не выдавай новые изменения за оцениваемую версию:
отдели разрешённую пользователем дальнейшую работу от зафиксированного релиза.
```

## 5. Финальное README-review

```text
Проверь root README как независимый технический эксперт без знания этого диалога.
Сверь docs/hackalem/11_README_REQUIREMENTS.md, п. 5.4.15–16/5.6.3–6 положения
и фактические файлы/команды текущего commit. По шагам воспроизведи основной сценарий.
Выяви отсутствующие зависимости, скрытый env, непроверенные обещания, отсутствующие файлы,
несуществующие команды, незадокументированные пороги/ограничения, несоответствие CSV и UI.
Отдельно: runtime без личных аккаунтов и платных сервисов, исходный starter disclosed,
точный измеренный pipeline runtime и ограничение <300 секунд.
Составь конкретный список исправлений и повторных проверок. Не объявляй успешный запуск,
если только прочитал README. Не подставляй вымышленные версии, hardware или время.
```
