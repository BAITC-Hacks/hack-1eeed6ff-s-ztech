# Качество, проверка AI и критерии приёмки

## 1. Что означает «довести до идеала» в пятичасовом окне

Практическая цель: **нет известных блокирующих дефектов, выполнены все must-have, выводы проверяемы, интерфейс профессионален, запуск воспроизводится другим человеком**. Нельзя гарантировать отсутствие любых ошибок или бесконечно переписывать готовый компонент. Каждая проверка имеет предмет, доказательство и время. После изменения повторять затронутые проверки; весь релизный прогон — после интеграции.

P0 — дисквалификация/невозможность запуска/повреждение исходников/потеря точности gid/утечка секрета. P1 — неверные суммы или роли относительно опубликованных правил, потерянные узлы, несогласованный API/UI/CSV, неработающий обязательный сценарий. P2 — ухудшение удобства или расширения без нарушения основного сценария. P3 — косметическое предпочтение. Релиз не допускает открытых P0/P1; P2 явно ограничить или убрать затронутую необязательную функцию. Нельзя просто переименовать P1 в P2 для зелёного отчёта.

## 3. Гейты этапов

| Gate | Минимум для PASS | Что делать при FAIL |
|---|---|---|
| G0 | Правила/время/remote известны, роли A/B, контракт, окружение | Исправить доступ/окружение; не писать несогласованный API |
| G1 | D01–D08, skeleton B, первый артефакт часа | Остановить новые признаки, исправить целостность |
| G2 | Все узлы с ролями/кластерами, CSV, первый реальный UI→API | Не добавлять расширения, завершить сквозной путь |
| G3 | Функциональные F01–F10, точность, поиск, ограничения; рабочий README и локальный smoke | Исправить P0/P1 в обязательном сценарии |
| G4 | Заморозка scope, расширения либо проверены, либо скрыты | Убрать незаконченное расширение |
| G5 | R01–R03, build/tests, полный measured run, README | Исправить точный блокер и повторить затронутые проверки |
| G6 | Итоговый SHA, артефакты и подтверждение подачи | Не заявлять завершение сдачи без факта |

В сокращённом маршруте G3 может не включать отдельный экспорт справки и E1/E2; все официальные must-have остаются. Если F09/F10 урезаны, явно записать ограничение продукта, не выдавать полный план за реализованный.

G3 — функциональная проверка интегрированного MVP. Независимый запуск из нового clone и финальная полнота README по F06 завершаются на G5; до G5 воспроизводимость полного релиза не считается подтверждённой.

## 4. Проверка AI после каждого этапа

Отдельный проход ревью получает: цель этапа, ссылки на спецификацию, diff, выполненные команды, выходы, известные ограничения. Если запускается другой инструмент, он сначала читает текущий git status и не правит файлы исполнителя. Дополнительный агент не является обязательным условием: важны независимый проход проверки и фактические доказательства, а не количество моделей.

Порядок проверки:

1. Соответствие официальным ограничениям, сохранность источников, отсутствие prebuilt core/скрытых внешних сервисов.
2. Математика, типы gid и денег, неполнота наблюдения, недопустимые причинные выводы.
3. Контракт API/CSV/UI и отсутствие hardcoded результатов.
4. Реальный запуск, ошибки и воспроизводимость.
5. Основной пользовательский сценарий и строгий визуал.

На каждую находку: severity, точный файл/сценарий, воспроизводимые шаги, ожидаемое/фактическое поведение, минимальное исправление. Комментарии «улучшить качество» без конкретного дефекта не блокируют этап. Не подменять отсутствие evidence словом PASS.

Шаблон записи в docs/progress/A.md или B.md:

```text
Этап: A2 / G2
Время Астана: фактическое начало и конец
Commit: реальный SHA после фиксации
Изменено: конкретные модули и поведение
Команды: точные команды, exit code, существенный вывод
Проверено: ID проверок и артефакты
Найдено: severity / сценарий / причина
Исправлено: изменение + повторная проверка
Открыто: конкретное ограничение или «нет известных P0/P1»
Статус: PASS / FAIL / BLOCKED
Следующий шаг: один конкретный этап
```

Это форма будущего отчёта; не заполнять её выдуманными SHA, временем или тестами. Сам факт наличия файла журнала не подтверждает выполнение работы.

## 5. Точная релизная проверка

На финальном commit: прочитать lock → создать новый venv → install → pipeline-only → verify-only → pytest → npm ci/test/build → локальный serve → браузерный smoke → offline smoke → выгрузки → демо с таймером. Если библиотека Playwright не успела установиться, выполнить те же сценарии вручную в реальном браузере, сохранить действия и screenshots и честно пометить отсутствие автоматического E2E. Это допустимая замена способа проверки, а не пропуск сценария.

Scan визуальных запретов по `web/src` и исходному HTML/SVG: gradient, linearGradient, radialGradient, backdrop-filter, декоративные filter/drop-shadow. Совпадение — повод проверить код, а не автоматический отказ из-за текста документа. Визуальный reviewer дополнительно оценивает композицию; отсутствие слова gradient не доказывает отсутствие AI-шаблона.

В финальном отчёте разделить: **реализовано / реально проверено / ограничено / не вошло**. Цель «максимум» не даёт права скрывать неполноту, называя mock готовым продуктом.
