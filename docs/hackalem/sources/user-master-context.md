## 1. Инструкция для AI, который будет помогать команде

Когда пользователь даст официальные Задачи/ТЗ HackAlem AI, действуй в таком порядке:

1. Сначала прочитай конкретное ТЗ каждой Задачи и извлеки обязательные deliverables, ограничения, критерии и веса, формат проверки, данные/API и требования к воспроизводимости.
2. Не придумывай отсутствующие требования. Помечай каждое утверждение как: **официальный факт / вывод / гипотеза / рекомендация**, когда это важно.
3. Не выбирай трек только по престижности, партнёру или ожидаемому числу команд. В HackAlem единый зачёт без квот по Задачам.
4. Оценивай каждую Задачу прежде всего по способности создать за 5 часов **полностью работающий, проверяемый end-to-end результат**.
5. Для каждого варианта решения оцени:
   - rubric fit;
   - feasibility за 5 часов;
   - time-to-first-working-demo;
   - data/API availability;
   - reliability;
   - reproducibility;
   - demoability;
   - реальную ценность;
   - инновационность;
   - масштабируемость;
   - соответствие навыкам команды;
   - технический и интеграционный риск.
6. Не предлагай принести заранее готовый продукт или основную функциональность задачи. Допустимы только технические заготовки, которые сами не являются решением задачи.
7. Любая архитектура должна быть hackathon-first: один golden path, минимум хрупких интеграций, понятный fallback, demo data, прозрачные логи/trace и README, по которому независимый эксперт запустит решение.
8. После выбора решения выдай:
   - requirements matrix;
   - MVP scope MUST/SHOULD/WON'T;
   - end-to-end flow;
   - architecture;
   - repo structure;
   - 5 почасовых milestones;
   - test plan;
   - reproducibility plan;
   - README outline;
   - Demo Day narrative;
   - список рисков и fallback.

## 2. Главные operational rules

### 2.1. Что разрешено заранее

Разрешены заранее подготовленные:

- технические компоненты;
- собственные библиотеки;
- шаблоны;
- инфраструктурные решения;
- dev tooling;
- open-source библиотеки, модели и инструменты.

Но они **не должны быть готовым продуктом или основной частью решения**, представляемого на HackAlem. Основная функциональность, соответствующая Задаче, должна быть разработана с 13:00 до 18:00.

### 2.2. AI и внешние сервисы

Разрешены любые AI-инструменты и AI-агенты для генерации/анализа кода, UI, архитектуры, данных, тестирования и документации. OpenAI Codex не обязателен, если конкретное ТЗ не говорит обратного.

Разрешены облачные платформы, внешние API, удалённые сервисы и системы разработки, но:

- личное присутствие на площадке остаётся обязательным;
- основная разработка и история проекта должны быть в официальном GitHub-репозитории;
- внешние зависимости должны быть воспроизводимы экспертами.

### 2.3. GitHub и почасовой прогресс

С 13:00 официальный GitHub-репозиторий, созданный Организатором через edu.astanahub.com, является основным рабочим репозиторием.

Обязательно:

- подтверждаемая история разработки;
- промежуточный результат по итогам **каждого часа**;
- реальные изменения: код, функционал, прототип, дизайн, архитектура, настройка модели, тестирование, данные и т. п.

Отсутствие подтверждённого результата хотя бы за один отчётный час — основание для дисквалификации.

### 2.4. Финальная версия

Официальный момент окончания — **18:00**. То, что зафиксировано Организатором на этот момент, считается итоговой версией. Изменения после 18:00 при оценке не учитываются.

### 2.5. README и воспроизводимость

README обязан содержать:

- описание решения и назначения;
- архитектуру;
- технологии;
- установку;
- запуск;
- зависимости;
- параметры окружения;
- пошаговый сценарий проверки основного функционала.

Если эксперт не может самостоятельно запустить проект по README, проект не допускается дальше. Дополнительные пояснения и исправления не принимаются.

Ключевая функциональность должна проверяться **без личных аккаунтов, персональных подписок или закрытых учётных записей участников**. Для внешних сервисов нужны demo credentials, test accounts либо другой независимый способ проверки.

## 3. Оценка

### 3.1. Технический отбор

Критерии технической оценки определяются **отдельным ТЗ конкретной Задачи**. Они могут отличаться по функциональности, технологиям, данным, способу проверки и распределению баллов.

Главное правило: после публикации Задач сначала оптимизируй решение под конкретный rubric Задачи, а не под абстрактные ожидания.

## 5. Как проектировать AI-агента под HackAlem

AI-агент оправдан, когда есть реальный цикл:

```text
Goal -> Observe -> Decide -> Call tool -> Validate -> Adapt -> Return result + trace
```

Минимальная рекомендуемая архитектура:

```text
User / Judge
    |
Frontend
    |
Backend API
    |
Agent / Orchestrator
    |-- LLM
    |-- Tool 1
    |-- Tool 2
    |-- Retrieval/Data
    |-- Validator
    |
State/DB
    |
Logs / traces / eval
```

Для 5 часов обычно лучше:

- 1 frontend;
- 1 backend;
- 1 основная модель;
- 2–4 полезных tools;
- простой state;
- явный validator;
- mock/demo data;
- fallback при сбое API;
- минимум auth;
- простое развёртывание.

Без острой необходимости избегай микросервисов, Kubernetes, сложного multi-agent swarm, 5+ LLM-провайдеров и инфраструктуры, которую невозможно объяснить/поднять за несколько минут.

## 8. Главные риски дисквалификации

1. Нет промежуточного результата за любой отчётный час.
2. Основная разработка вне официального GitHub.
3. Нет подтверждаемой истории разработки.
4. Заранее принесён готовый продукт/core functionality.
5. Скрыто существенное использование стороннего решения.
6. Нарушены лицензии/права третьих лиц.
7. Проект не запускается по README.
8. Для проверки нужен личный закрытый аккаунт участника.
9. Участник нарушил правила обязательного присутствия.
10. Попытка вмешательства в сети/проекты/инфраструктуру других команд.
11. Использование вредоносного кода/несанкционированного доступа.
12. Расчёт на исправление оцениваемой версии после 18:00.

## 9. Организационные и правовые нюансы

- Участник должен быть 18+ на дату хакатона и соответствовать хотя бы одному из квалификационных требований из раздела 5.1.3.
- Один участник — одна команда и один проект, если Организатор не разрешил иное.
- После check-in и во время соревновательной части разработка должна идти на площадке.
- Временный выход — только с предварительного разрешения; суммарно не более 60 минут, кроме экстренных обстоятельств.
- Команда сама обеспечивает ноутбук, зарядку, ПО, аккаунты и LAN-переходник.
- Организатор/AI-судья/эксперты могут проверять репозиторий, код, архитектуру, функциональность, заявленные результаты и вклад участников.
- Участники дают Организатору широкое безвозмездное право использования результатов без ограничения срока и территории в целях, связанных с Хакатоном/экосистемой/образованием/инновациями.
- Команда гарантирует наличие прав на код, модели, данные, дизайн и иные материалы и соблюдение сторонних лицензий.
- Участие означает согласие на предусмотренную правилами обработку персональных данных, фото/видеосъёмку и публикацию материалов.
- После начала соревновательной части Организатор не должен ретроспективно менять обязательные требования/критерии, кроме оговорённых исключений.

## 13. Полный раздел 5 Положения

### 5. Порядок организации и проведения Хакатона

5.1. Участники и состав команд

5.1.1. Участие в Хакатоне является добровольным и бесплатным, если Организатором заранее не установлено иное.

5.1.2. К участию допускаются физические лица, достигшие возраста 18 (восемнадцати) лет на дату проведения Хакатона, прошедшие регистрацию, получившие подтверждение участия и соответствующие хотя бы одному из требований, предусмотренных пунктом 5.1.3 настоящего Положения.

5.1.3. Требования к участникам:

- Опыт или образование в сфере разработки: участник работает в сфере IT либо обучается по соответствующему направлению.
- Статус студента или молодого специалиста: участник является студентом либо обучался очно в течение последних 12 месяцев по специальности, связанной с IT, программированием, инженерией, технологиями, математикой или дизайном цифровых продуктов.
- IT-энтузиаст: участник имеет собственные проекты, прототипы, приложения, исследования или иные разработки, подтверждающие его навыки.

5.1.4. Участие в Хакатоне осуществляется в составе Команды.

5.1.4.1. Участники, выступающие индивидуально, оцениваются на общих основаниях с Командами и не получают преимуществ или ограничений, связанных с количеством участников в составе Проекта.

5.1.5. Капитан отвечает за взаимодействие с Организатором, корректность регистрационных данных Команды, своевременную подачу Проекта и предоставление необходимых документов.

5.1.6. Один участник вправе состоять только в одной команде и представлять только один Проект, если Организатором не установлено иное.

5.1.7. Участник обязан лично присутствовать на площадке Хакатона с момента прохождения check-in до официального завершения соревновательной части. После прохождения check-in и начала соревновательной части участник не вправе покидать территорию проведения Хакатона и осуществлять разработку Проекта вне площадки. В период соревновательной части разработка Проекта должна осуществляться исключительно на площадке Хакатона.

5.1.7.1. Временный выход с площадки допускается только с предварительного разрешения Организатора. Общая продолжительность отсутствия участника не может превышать 60 минут. Превышение установленного времени отсутствия без согласования с Организатором является основанием для дисквалификации участника либо Команды.
