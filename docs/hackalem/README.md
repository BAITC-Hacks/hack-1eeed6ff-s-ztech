# Neverlose · Граф денег — пакет разработки

Версия плана: 1.0, 23 сентября 2026. Команда: два человека, у каждого Codex и Claude Code. Выбран трек «Финансы», заказчик Freedom. Формат продукта: рабочее место AML-аналитика. Репозиторий: [официальный репозиторий команды](https://github.com/BAITC-Hacks/hack-1eeed6ff-s-ztech).

**Статус: подробное проектирование и аудит исходных данных. Приложение ещё не реализовано.** Наличие этого пакета, датасета и оригинального starter не означает прохождение функциональных проверок или готовность к сдаче. Все команды будущего приложения в документах — контракт реализации, а не уже работающие команды.

## Что строим

**Neverlose — рабочее место, которое показывает, кого проверять первым, какие наблюдения поддерживают гипотезу и какие данные могут её опровергнуть.** Главное отличие: цепочка «приоритет → признаки роли → исходные переводы → альтернативное объяснение → следующий запрос данных». Красивая карта здесь помогает проверить решение, а не заменяет расчёт.

Уникальность относительно всех неизвестных участников и победу гарантировать нельзя. Предлагается конкретное, проверяемое отличие от обычного графа с непрозрачным рейтингом. Базовая версия полностью локальная; платный LLM API не нужен для работы приложения и проверки жюри. AI используется при разработке; объяснения в MVP формируются из рассчитанных фактов.

## Персональные задания

- **Мейрам — [личное ТЗ](MEIRAM.md):** данные, аналитическое ядро, API, CSV, README и выпуск.
- **Алишер — [личное ТЗ](ALISHER.md):** интерфейс, граф, карточки/гипотезы, браузерная проверка и демо.

## С чего начать вдвоём

1. Оба читают этот файл, [контекст](08_SESSION_CONTEXT.md), [правила](07_RULES_DELIVERY.md) и [контракт](03_ARCHITECTURE_CONTRACTS.md).
2. Мейрам (A) берёт данные, алгоритмы, API, CSV и выпуск. Алишер (B) — интерфейс, интеграцию, визуальную проверку и демо. Файлы и передачи результатов перечислены в [плане](05_IMPLEMENTATION_PLAN.md).
3. Каждый запускает свою AI-сессию с соответствующим промптом из [09_PROMPTS.md](09_PROMPTS.md). Один AI пишет в своём checkout; второй проверяет read-only. Два процесса не правят одновременно одни файлы.
4. Первая цель — сквозной путь от исходных parquet до настоящей карточки узла. Затем доводим обязательную функциональность и только потом добавляем расширения.
5. Каждый этап закрывается записью фактического результата и проверок в `docs/progress/`. Статус проекта обновляется в [STATUS.md](STATUS.md).
